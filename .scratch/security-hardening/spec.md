# Spec：安全加固——消除审计发现的漏洞

## Problem Statement

对本应用（HEIC 图片转换器）做了一轮安全审计，发现一批真实漏洞。作为用户，我面临的风险包括：

1. 一个几 KB 的恶意 HEIC 文件就可能耗尽我的内存、让应用崩溃甚至整机卡死（图片炸弹）。
2. 转换输出可能**静默覆盖**我输出目录里已有的同名文件；若输出目录中被预置了符号链接，还可能改写我任意的可写文件。
3. 应用的 webview 被授予了它根本用不到的宽权限（可写 `$HOME/**`、`/mnt/**` 的 fs 写权限、无 scope 的打开路径权限）——一旦出现任何前端注入，会被放大为持久化入侵（如写 `~/.ssh/authorized_keys`）。
4. "清空失败"按钮会连待转换队列一起清空；转换进行中点击会让转换状态与界面彻底脱节。
5. 文件列表里文件大小可能永远显示"加载中…"（`stat` 权限缺 scope，被后端拒绝后错误被静默吞掉）。
6. 转换任务在异步运行时线程上同步执行，且 Linux 常驻通知可无限期占住一个线程，连续多批转换可能把应用拖死。
7. 其他缺陷：任意 JS 可调用强制退出绕过关闭确认、FIFO/设备文件输入可永久阻塞转换线程、不同目录同名文件竞争同一输出、调试日志残留、错误原文直接弹给用户等。

## Solution

一轮聚焦的安全加固，覆盖审计确认的全部发现：

- **输入侧**：Rust 后端不再信任前端参数——校验输入是普通文件、扩展名白名单、数量上限、输出目录来源；HEIC 解码前强制尺寸/内存上限，超限返回用户友好的错误而不是崩溃。
- **输出侧**：写文件改用"已存在即失败"策略，拒绝跟随符号链接，同批次同名目标去重，绝不静默覆盖用户文件。
- **权限面**：删除所有"授予了但从未使用"的 capability（fs 写权限、打开路径、通知默认权限），给真正使用的 `stat` 补上精确 scope，让文件大小正常显示。
- **健壮性**：长耗时转换移出 async 运行时线程；停止标志与批次解耦，加并发批次单飞闸；移除前端零调用的强制退出命令。
- **前端体验**："清空失败"只清失败列表，所有清空/危险按钮在转换中禁用；错误信息映射为用户友好文案，原始错误只进日志。

## User Stories

1. As a 用户, I want a 恶意构造的超大尺寸 HEIC 文件被转换前就拒绝, so that 我的机器不会因图片炸弹而内存耗尽或崩溃。
2. As a 用户, I want HEIC 解码前按文件头声明的宽高做上限校验, so that 几 KB 的文件不能要求分配几十 GB 的缓冲区。
3. As a 用户, I want 超限时看到一条明确的用户友好错误（而非崩溃或"转换失败"+原始错误）, so that 我知道是文件问题而不是应用坏了。
4. As a 用户, I want 输出目录里已存在同名文件时不被静默覆盖, so that 我的旧照片不会在批量转换中丢失。
5. As a 用户, I want 同名冲突时得到明确错误或自动加序号, so that 我能立刻发现并处理冲突。
6. As a 用户, I want 输出写入不跟随符号链接, so that 别人无法借输出目录改写我目录之外的文件。
7. As a 用户, I want 应用的可写性探测探针也不跟随符号链接且不误删用户文件, so that 探测本身不成为攻击面。
8. As a 用户, I want 只能选择已确认的输出目录进行写入, so that 任何前端异常都不能在任意路径创建目录树或写文件。
9. As a 用户, I want 只有普通文件（非 FIFO/设备文件/目录）会被送入转换, so that 拖入一个特殊文件不会让转换线程永久卡死。
10. As a 用户, I want 转换输入的数量有上限, so that 一次误操作不会锁死整个应用。
11. As a 用户, I want 同批次中不同目录的同名文件不会竞争同一个输出文件, so that 批量转换的产物不会互相截断损坏。
12. As a 用户, I want 应用不再持有它用不到的宽权限（`$HOME/**` 写文件、无 scope 打开路径、全量通知）, so that 即使前端被注入也无法被利用来做持久化入侵。
13. As a 用户, I want 文件大小在列表中正常加载并显示, so that 我不用对着永远转圈的"加载中…"猜测文件多大。
14. As a 用户, I want "清空失败"只清空失败列表, so that 我清理失败项时不会连待转换队列一起丢掉。
15. As a 用户, I want 转换进行中所有清空类按钮被禁用, so that 我不会在转换中途把状态搞乱。
16. As a 用户, I want 连续多批转换时应用不会越跑越卡直至假死, so that 我可以放心地挂一整晚批量任务。
17. As a 用户, I want 通知的等待不再占用转换运行的线程, so that 通知没被点掉之前应用其他功能仍正常。
18. As a 用户, I want 应用在转换写盘途中不会被任意强制退出, so that 不会产生截断的半成品文件。
19. As a 用户, I want 我点"停止"只停当前批次, so that 停止信号不会与其他批次互相干扰。
20. As a 用户, I want 已有批次在跑时再次发起转换会被明确拒绝而不是叠加并发, so that CPU 和内存不会被双倍占用。
21. As a 用户, I want 弹窗里的错误是可读的简短文案, so that 我不需要面对一串绝对路径和 IO 错误细节。
22. As a 用户, I want 原始错误细节只写进应用日志, so that 排查问题时信息仍在但不打扰我。
23. As a 用户, I want 错误级日志与页面端不出现我的完整目录路径、也不把日志转发给页面脚本, so that 我的目录结构不暴露给同源 JS（debug/warn 级完整路径仅保留在本地日志文件中，供排障使用）。
24. As a 用户, I want 生产构建的控制台没有残留的调试输出, so that 界面行为干净、与项目其余部分的日志风格一致。
25. As a 用户, I want 关闭/退出路径上的异步失败被妥善处理, so that 不会出现"点了退出没反应"。
26. As a 用户, I want 关闭窗口时的"转换中确认"仍然生效且无法被绕过, so that 我不会误丢正在进行的任务。
27. As a 维护者, I want capability 配置有一条回归测试断言多余权限已被移除, so that 未来无意间加回宽权限会立刻被 CI 拦住。
28. As a 维护者, I want 输入校验、写安全策略各有覆盖其外部行为的测试, so that 后续重构不会悄悄拆掉这些防线。
29. As a 维护者, I want store 层对"只清失败、不清队列"有单元测试, so that 前端状态机的这条不变量不被破坏。
30. As a 维护者, I want CSP 补上 `object-src 'none'; base-uri 'self'`, so that 生产响应头的加固面完整。
31. As a 维护者, I want 内存池要么修复复用分支的越界隐患、要么直接删除, so that 代码库里不留潜伏的 panic/死代码。
32. As a 维护者, I want 审计结论（哪些面已确认无问题：路径穿越、命令注入、XSS、密钥硬编码）在本 spec 的 Further Notes 中声明即可, so that 下一轮审计不用从零重查。
33. As a 用户, I want "已完成"列表同时显示源文件名与实际生成的文件名（以 → 分隔）, so that 输出加序号兜底（如 `photo (1).jpg`）时我能直接看到真实产物名而不必打开目录确认。

## Implementation Decisions

- **校验下沉到 Rust 命令层**：前端的过滤只是 UI 级别，所有输入/输出校验（文件类型、扩展名白名单、数量上限、输出目录来源）必须在命令处理入口完成。前端校验保留，仅作为即时反馈。
- **输出目录来源约束**：命令层记住由目录对话框/下载目录查询确认过的输出目录，只接受与之一致的路径；不再对任意传入路径执行目录创建与写入。
- **写盘策略**：所有输出写入统一走"创建即失败"（已存在则报错或加序号）语义；写入不跟随符号链接——目标名已被预置符号链接占用时不覆盖、不跟随，自动改用带序号的名称（如 `photo (1).jpg`）并成功。可写性探测同样用"创建即失败"方式，探测失败即返回错误，不再先写后删固定文件名探针。
- **HEIC 解码限额**：解码前读取图像头声明的宽高并施加上限（数量级 16384×16384），同时对输入文件大小设阈值；超限返回专用错误变体，经既有的用户友好错误映射层输出。通用格式路径已有的 `image` crate 分配限额（512 MiB）保持不变。
- **错误模型扩展**：在既有的转换错误枚举上新增"输入不合格""尺寸超限""输出冲突"等变体，全部接入统一的用户友好文案映射；面向用户的弹窗只展示映射后的文案，原始错误仅写日志。
- **能力配置收敛**：移除 `fs:allow-write-file`、`opener:allow-open-path`、`notification:default` 三条未使用权限；给 `fs:allow-stat` 补精确 scope（限定图片/下载等用户目录，不用 `$HOME/**`）。转换写盘走 Rust 命令，不依赖 fs 插件写权限。
- **命令注册收敛**：从 invoke 处理器移除前端零调用的强制退出命令，关闭确认只能经由既有窗口关闭流程。
- **并发与停止语义**：批次转换整体移入阻塞线程执行（async 运行时的 blocking 上下文），不再占用 async worker；停止标志改为批次局部，另加单飞闸——已有批次在跑时新批次直接返回错误。Linux 常驻通知的等待移出 async 上下文。
- **输入预检**：转换入口用文件元数据判断"是普通文件"才进入转换队列（顺带排除指向目录/设备的符号链接）；同批次构建输出对时按目标路径去重，冲突者加序号或报错。
- **前端状态**：新增只清失败列表的 action；清空类按钮在转换中/准备中一律禁用。
- **日志脱敏**：错误日志只记录文件名或脱敏后的路径；生产日志不再附加把同源 JS 作为输出目标的 sink。
- **杂项清理**：移除标题栏残留调试输出；对既有日志调用补统一的 rejection 兜底；修正 store 中 active tab 参数类型与实际值域不一致；CSP 响应头补 `object-src 'none'; base-uri 'self'`；内存池复用分支修复（复用时恢复缓冲区长度）——鉴于当前无调用方，倾向直接删除内存池，实施时按最小改动原则取舍。
- **回归测试入 CI**：能力配置断言测试与既有测试套件一起在 CI 运行。
- **已完成列表展示实际输出名**：已完成卡片显示 `源文件名 → 生成文件名`，其中生成文件名取转换完成事件回报的输出路径（即路径规划阶段确定的最终名，含加序号兜底结果）的文件名部分。

## Testing Decisions

- **好测试的定义**：只断言外部可观察行为——给定输入文件/参数，观察写出了什么文件、返回了什么错误、状态变成了什么；不断言内部函数被调用次数、不 mock 掉被测逻辑本身。
- **主 seam（已有）：Rust 集成测试 `src-tauri/tests/`**，纯 Rust、无需 Tauri 运行环境：
  - 路径与写安全（扩展既有 path 测试，用 `tempfile`）：同名已存在→加序号不覆盖；输出目标为符号链接→不覆盖不跟随、改用序号名称；探针不跟随符号链接；目录创建仅限授权目录。
  - 输入校验（对新抽出的纯校验函数）：非普通文件/设备/FIFO、非法扩展名、超数量上限、越界输出目录 → 均被拒绝。
  - 图片炸弹：构造超限尺寸的 HEIC 头文件与超大文件 → 返回"尺寸超限"类错误而非 panic；正常样例（`test-data/`）仍通过。
  - 能力配置断言：解析 `capabilities/default.json`，断言被删权限不再出现、`stat` 带 scope——防回归。
- **次 seam（已有）：Vitest 单测 `src/__tests__/unit/`**：
  - store：`clearErrors()` 只清失败列表、保留待转换队列与转换状态；既有 store 测试作为先例。
  - 组件：清空按钮在转换中禁用；标题栏不再输出调试日志。
- **不测（靠 code review + 实机验证）**：async→阻塞线程的改造、通知等待线程迁移、单飞闸的实际调度行为、日志 sink 调整。
- **先例**：`path_test.rs`（tempfile 驱动的路径行为测试）、`common_test.rs`（保存格式行为）、`conversionStore.test.ts`（状态机不变量）。

## Out of Scope

- 上游 C 库（libheif/libde265 系统库）自身的 CVE：不属于本仓库代码，Rust 侧先行限额即是缓解手段。

- 功能性重构、UI 改版、性能优化（除阻塞线程改造这一健壮性修复外）。

## Further Notes

- 审计已确认**无问题**的面（下轮可直接跳过）：路径穿越（stem/白名单精确匹配）、外部进程与命令注入（全仓无 `std::process`/shell/dlopen）、XSS（零 `v-html`/`innerHTML`/`eval`）、硬编码密钥、blob 文件名注入、asset protocol（未启用）。
- **Backlog（code-review 裁决，本轮不处理）**：`confirm_output_folder` 为公开 invoke、接受任意字符串，被注入的 JS 可自证任意路径——该闸的目标是防前端状态失同步而非防注入；如需防注入可后续加"对话框一次性 token、后端核验"机制。
- `stat` scope 裁决：实机确认从 `/media` 等目录拖入文件也能正常读取与显示，符合预期，无需处理；四个标准目录的精确 scope 维持。
- 审计发现按严重度排序：高（图片炸弹、多余写权限、无 scope 打开路径、覆盖/symlink、输出目录信任）→ 中（stat scope、清空按钮、阻塞 async worker）→ 低（其余）。实施顺序建议按此优先级。
